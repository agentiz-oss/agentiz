# `/dashboard/agentiz-pipelines` — редактор пайплайна проекта

> **Состояние «до»: 8 сентября 2026.** Описанные здесь экраны и адреса заменены переносом
> панели на дерево `/agentiz` — читайте это как исходные данные того решения, а не как описание
> нынешней панели. Как она устроена сейчас — [`../guides/panel-ui.md`](../guides/panel-ui.md).

`AgentizPipelines.tsx`, 834 строки — второй по размеру кастомный модуль. Один проект — один
редактируемый `PipelineSpec` (выбор через `<select>` в шапке, «Default pipeline · default» на
скриншоте — сейчас на UI нет явного «создать второй пайплайн для этого проекта», хотя модель это
допускает, см. `08-generic-crud-models.md`).

![Пайплайны](screenshots/agentiz-pipelines.png)

Сверху вниз, всё в одной длинной форме без вкладок (все правки уходят одним PATCH,
`updatePipelineSpec`, — то есть редактор держит **черновик всей спеки** в состоянии и шлёт целиком
при любом чейндже; отдельного «Сохранить» не видно на скриншоте, значит сохранение либо
автоматическое на blur/change для каждого поля, либо кнопка вне видимой области — стоит проверить
перед переразбивкой, чтобы не потерять поведение):

1. **«ACP-агенты и пайплайн»** — для каждой роли проекта (`decider`/`investigator`/`reporter`, имя
   роли и её `key` — `AgentRole`) выпадающий список `Выберите ACP-агента` (`setRoleAcpProvider`,
   переключает Codex/Claude на уровне роли — это то, что в `AGENTS.md` названо «сначала выберите
   Codex или Claude для роли»).
2. **«С чем работает пайплайн»** — два связанных `<select>`: `spec.source` (`Репозиторий проекта
   (GitHub/GitLab)` или готовая папка воркера) и, если выбран репозиторий, второй селект «Репозиторий
   задачи» / т.п. Текст-подсказка ссылается на страницу «Репозитории» (`agentiz-repos`) и, для
   `worker_workspace`, на страницу «Воркеры» (блок «Готовые папки для пайплайнов») — то есть эта
   форма **читает**, но не создаёт готовые папки/репозитории, только выбирает уже заведённые там.
   Для `worker_workspace` — форма ввода абсолютного пути + кнопка `Сохранить путь`
   (`AgentizPipelines.tsx:163`), чекбокс `stashDirty`-подобная настройка (строка ~665) и, для
   финального действия — чекбокс `Требовать подтверждение` (`finalAction.requireApproval`,
   строка 732) и напоминание про «Откуда разрешён Git push» на странице «Воркеры», если push не
   настроен.
3. **«Запускать пайплайн после нового сообщения пользователя»** — один чекбокс
   (`spec.hooks`-соседняя настройка триггера по комментарию — это ручной аналог workflow-триггера
   `agentiz.task.comment`, но без графа, см. `AGENTS.md`).
4. **«Скрипты вокруг стадий»** — два чекбокса-раскрывашки `Перед стадиями` / `После стадией`
   (`PipelineHooksSection.tsx`/`HookScriptEditor.tsx`, отдельные подкомпоненты в
   `adminizer/modules/hooks/`) — редактор bash/node-скрипта хука, с описанием, какие
   `AGENTIZ_*`-переменные окружения ему доступны (см. `hookEnv.ts` в `AGENTS.md`).
5. **«Стадии»** — по одной строке на `spec.stages[]`: номер+ключ (`#1 investigate`), `<select>`
   роли (`Расследователь (investigator)`), `<select>` окружения (`Host`/Docker — судя по
   подписи), и поле «модель роли» (placeholder показывает модель по умолчанию из роли —
   `claude-sonnet-5` и т.п. — переопределение только для этой стадии, см. `AGENTS.md` про
   `stage.model`).
6. **«Уведомления»** — та же переиспользуемая врезка `NotificationPolicySection` с кнопкой
   `Настроить`, что и на хабе проекта (см. `05-members-and-notifications.md`) — здесь она читает
   `getOverrides` для этого конкретного `pipelineSpecId`.

Все данные тянутся с **пяти разных** `axios.get` на пять разных URL-баз (`HOME_URL`, `REPOS_URL`,
`WORKERS_URL`, `API_URL`, `NOTIFICATIONS_URL`) — то есть этот один экран знает о пяти чужих
роутерах (`layers/app-agentiz/lib/{repositoryRoutes,workerRoutes,pipelineRoutes,notificationRoutes}.ts`
плюс `index.ts` `/agentiz`), что видно уже по количеству `_method`-веток внутри одного файла.
Для редизайна это значит: логика «что показывать на экране пайплайна» размазана по бэкенду не
меньше, чем по фронту — растащить на отдельные вкладки/шаги здесь дешевле начать с бэка (отдельный
`_method` на вкладку уже есть), чем с фронта.
