# Что мешает при переразбивке — конкретные находки

> **Состояние «до»: 8 сентября 2026.** Описанные здесь экраны и адреса заменены переносом
> панели на дерево `/agentiz` — читайте это как исходные данные того решения, а не как описание
> нынешней панели. Как она устроена сейчас — [`../guides/panel-ui.md`](../guides/panel-ui.md).

Собрано по ходу ревизии, с файлами/строками, чтобы каждый пункт можно было сразу пойти проверить,
а не гадать, о чём речь.

## 1. Две несовместимые дизайн-системы на одних и тех же экранах

Adminizer сам по себе — shadcn/ui (скруглённые инпуты, `focus-visible` кольца, консистентные
кнопки/тени — видно на странице логина и на любом типовом CRUD-экране, `08-generic-crud-models.md`).
Все 10 кастомных модулей Agentiz (`layers/app-agentiz/adminizer/modules/*.tsx` +
`AgentizGithub.tsx`/`AgentizGitlab.tsx`) написаны сырыми `<button>`/`<select>`/`<input>` с ручными
Tailwind-классами (`rounded border px-3 py-1.5 text-sm font-medium` и вариации), **при том что**
`vite.config.ts` уже экспортирует `@/components/ui/{button,card,dialog,input,label,select,tabs,textarea}`
как готовый глобал (`viteExternalsPlugin`, см. `00-overview.md`) — то есть подключение стоит
буквально `import { Button } from "@/components/ui/button"`, без изменения сборки. Это самая
дешёвая и самая заметная правка: визуально «два разных продукта» превратятся в один без единой
смены бизнес-логики.

## 2. Три независимые копии одной формы «ответить агенту»

`AgentizRunDetail.tsx:589-641` и `AgentizInteractions.tsx` (целиком, 157 строк) рендерят один и тот
же JSON Schema → форму (`humanInputSchema.ts`, `humanInputChoices`) с одними и теми же тремя
кнопками (`Ответить`/`Отказаться`/`Отменить запрос`) — независимо друг от друга. Следующее поле
типа в схеме придётся добавлять в двух местах synchronно; уже сейчас нет гарантии, что они не
разошлись незаметно. Кандидат на общий компонент `HumanInputForm`.

## 3. Один и тот же виджет уведомлений встроен в три экрана — и это единственный переиспользуемый бизнес-компонент

`NotificationPolicySection.tsx` используется на хабе проекта, на экране пайплайна и на отдельной
странице `/dashboard/agentiz-notifications` (`05-members-and-notifications.md`). Это единственный
пример в проекте, когда переиспользование реально сделано, а не продублировано copy-paste —
стоит взять за образец подхода, а не изобретать новый паттерн для остального.

## 4. Меню не отражает структуру продукта

`00-overview.md`: половина кастомных экранов (`agentiz-pipelines`, `agentiz-workers`,
`agentiz-notifications`, `agentiz-repos`, `agentiz-viewer`, `agentiz-github`) не в боковом меню —
попасть на них можно только кликом с хаба проекта или (для `github`/`gitlab`) друг с друга. При
этом почти одноимённые generic-CRUD модели (`Agentiz Workers`, `Repositories`) в меню **есть** —
человек, доверившийся сайдбару, попадёт на сырую таблицу вместо человеческого экрана. Асимметрия
`agentiz-github`/`agentiz-gitlab` в меню (только gitlab виден) выглядит скорее упущением, чем
решением — стоит сверить с git-историей перед тем как чинить.

## 5. Пять-семь источников данных на одном экране, RPC поверх одного POST вместо REST

`AgentizPipelines.tsx` и `AgentizWorkers.tsx` каждый обращаются к 5 разным базовым URL
(`HOME_URL`, `REPOS_URL`, `WORKERS_URL`, свой `API_URL`, `NOTIFICATIONS_URL`), и внутри каждого
`API_URL` — RPC-диспетчер по полю `_method` (`{"_method": "getProjects"}` вместо `GET /projects`).
Это не проблема сама по себе, но означает, что **разбить экран на вкладки/подстраницы дешевле
начинать с бэкенда** (там уже есть естественные границы по `_method`), а не пытаться резать по
одному fat-компоненту на фронте.

## 6. Один файл — 1500 строк (`AgentizTasks.tsx`), 1450 строк (`AgentizWorkers.tsx`), 834 строки (`AgentizPipelines.tsx`), 766 строк (`AgentizRunDetail.tsx`)

Ни один кастомный экран не разбит на подкомпоненты, кроме `AgentizHome.tsx` (свой `NavCard`),
`AgentizPipelines.tsx` (выносит `PipelineHooksSection`/`HookScriptEditor`) и
`AgentizRunDetail.tsx`/`AgentizTasks.tsx` (используют общий `DiffViewer`). Список задач, деталь
задачи, форма создания задачи, список источников и форма добавления источника — всё в одном
`AgentizTasks.tsx`. При переразбивке стоит для начала просто растащить по файлам вдоль уже видимых
на скриншотах границ (список / деталь / формы), не меняя логику — это уже сильно снизит
когнитивную нагрузку на следующего разработчика, независимо от решения по дизайн-системе.

## 7. `PipelineSpec` — вторая по важности сущность продукта, без нормальной формы

`08-generic-crud-models.md`: у `PipelineSpec` нет собственного экрана редактирования произвольной
записи — только (а) кастомный редактор *текущего* пайплайна проекта на `/dashboard/agentiz-pipelines`
(который правит ровно один `PipelineSpec`, выбранный из `<select>`, RPC-запросом целиком) и
(б) сырая JSON-форма Adminizer. Если у проекта несколько пайплайнов — второй и далее правится либо
руками в JSON, либо через MCP. Стоит явно решить: либо `AgentizPipelines.tsx` учится работать с
произвольным числом спек проекта (тогда generic-форма не нужна вовсе), либо генерик-форма для
`PipelineSpec` получает человеческие виджеты под её JSON-поля (`spec.stages[]`,
`spec.source`, `spec.hooks` — те же типы данных, что уже разобраны кастомным редактором).

## 8. Формы отправляют весь объект целиком, а не патчи по полю

`AgentizPipelines.tsx:315` — `updatePipelineSpec` шлёт **весь** `build(pipelineSpec.spec)` на любое
изменение одного поля. Для UI это значит: не видно явной кнопки «Сохранить» на уровне формы
(вероятно, автосейв на каждое изменение) — стоит подтвердить наблюдение вживую (кликнуть в поле,
посмотреть Network) перед тем как проектировать разбивку на шаги/вкладки с явным подтверждением,
чтобы не потерять текущее поведение автосохранения, если на него кто-то полагается.

## 9. Пустые состояния — только текст, без единого стиля

Каждый экран сам решает, как выглядит «данных нет»: где-то абзац с объяснением, что делать
(`agentiz-workers`, `agentiz-github`/`gitlab`), где-то одна нейтральная строка (`agentiz-interactions`,
`agentiz-repos`). Стоит унифицировать хотя бы контейнер (сейчас это то `rounded-lg border p-4`, то
просто параграф без рамки — сравните скриншоты `agentiz-interactions.png` и `agentiz-workers.png`).
