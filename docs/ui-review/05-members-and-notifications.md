# Участники, уведомления, переиспользуемая секция политики

> **Состояние «до»: 8 сентября 2026.** Описанные здесь экраны и адреса заменены переносом
> панели на дерево `/agentiz` — читайте это как исходные данные того решения, а не как описание
> нынешней панели. Как она устроена сейчас — [`../guides/panel-ui.md`](../guides/panel-ui.md).

## `/dashboard/agentiz-members` (`AgentizMembers.tsx`, 370 строк)

![Участники](screenshots/agentiz-members.png)

Таблица участников выбранного проекта: человек (имя+логин), роль (`Agentiz · Владелец` — имя
группы панели + человекочитаемая метка роли), список токенов роли мелким текстом под меткой, кто и
когда выдал. Кнопка `Пригласить` в шапке раскрывает панель:

- поле поиска + кнопка `Поиск` → `candidates` (ищет существующих пользователей панели по
  логину/имени, не заводит нового);
- список найденных кандидатов, у каждого — кнопка добавить в проект с ролью;
- `закрыть`, чтобы свернуть без действия.

Роль — это, как явно говорит подзаголовок страницы, «обычная группа панели»: `agentiz-members`
не создаёт новых сущностей ролей, только выдаёт/отбирает членство (`AgentProjectMember`) —
подробности инварианта в `AGENTS.md` («Доступ к проекту — три отдельных механики»).

## `/dashboard/agentiz-notifications` (`AgentizNotifications.tsx`, 126 строк)

![Уведомления](screenshots/agentiz-notifications.png)

Тонкая обёртка вокруг `NotificationPolicySection` (ниже) для **самого общего** уровня —
`defaults` — плюс отдельный блок **«Где переопределено»**: список проектов/пайплайнов, у которых
есть собственные записи в `AGENTIZ_NOTIFY_POLICY`, каждый — ссылка `настроить →` прямо на тот
экран, где это переопределение живёт (хаб проекта или экран пайплайна) — то есть эта страница не
редактирует чужие переопределения сама, только показывает, где их искать. Пустое «Нигде — всё
работает по общим правилам выше» — как на скриншоте.

## `NotificationPolicySection.tsx` — общий виджет (273 строки, встроен 3 раза)

Один и тот же React-компонент используется на **трёх** экранах — здесь, на хабе проекта
(`AgentizHome.tsx`) и на экране пайплайна (`AgentizPipelines.tsx`) — с разным `scope`/`id`,
который и определяет, что именно правится (`defaults` / `projects[projectId]` /
`pipelines[specId]` — три уровня из `AGENTS.md`, «одна json-настройка `AGENTIZ_NOTIFY_POLICY`»).
Это единственный по-настоящему переиспользуемый бизнес-компонент во всей ревизии (в отличие от
`DiffViewer`, который переиспользуется формально, но с одним вызывающим на файл).

Раскрывается кнопкой `Настроить`/`Настроено (N)` (число активных переопределений в свёрнутом
виде). Развёрнутое содержимое:

- Предупреждение жёлтым, если `AGENTIZ_NOTIFY_POLICY` задана переменной окружения — она **целиком**
  перекрывает сохранённый документ (ровно то поведение из `AGENTS.md`: «env wins и затеняет
  документ целиком»), с явным текстом «правки отсюда сохранятся, но применяться будет значение из
  .env» — то есть форма не блокируется, но откровенно предупреждает, что бесполезна прямо сейчас.
- Чекбокс `Замьютить всё` (кроме типов с явным overrides ниже).
- Таблица: строка на каждый тип события (`activityTypes.ts`) — колонки «Пуш» (`будить`/`тихо`/
  `не слать`/«наследуется (X)»), «Колокольчик» (`слать`/`не слать`/«наследуется (X)»), «Сейчас»
  (вычисленный эффективный результат словами).
- Три кнопки: `Сохранить` (активна только если `dirty`), `Отменить правки` (откатить черновик к
  загруженному), `Сбросить к наследованию` (`save(null)` — стереть весь override уровня, вернуться
  к более общему).
- Строка-напоминание: «Лента активностей пишется всегда — политика отключает только доставку»
  (то же инвариант, что в `AGENTS.md` про `ActivityService.record()`).

Для переразбивки: раз виджет один на три места, его форма (таблица типов × два канала) — это уже
почти самостоятельная страница «Уведомления», и вопрос «встраивать as-is или выносить в модалку/
отдельный роут» стоит решать один раз для всех трёх точек входа, а не по отдельности.
