# Настройка workspace Git review в админке

Этот режим нужен, когда pipeline работает не через checkout, который Agentiz сам клонирует по
git provider, а прямо в подготовленной папке на конкретном worker. В таком режиме Agentiz может:

- только оставить результат в задаче;
- ничего не делать после выполнения;
- сохранить diff, дождаться подтверждения и затем сделать `commit` + `push` из этой папки.

`commit_and_pr` для `worker_workspace` не используется: PR/MR открывает hosting provider, а здесь
доставка выполняется локальным Git на том же worker.

## Что должно быть готово заранее

- Worker уже зарегистрирован и находится в состоянии `active`.
- На машине worker уже существует Git checkout нужного репозитория.
- У этого checkout настроен корректный remote, обычно `origin`.

Привязанный `Project Repository` **не нужен**: папка на воркере пушит в свой собственный remote.
Привязка остаётся опциональной — если её указать, Agentiz дополнительно сверит, что remote папки
совпадает с `cloneUrl` этого репозитория.

Папку pipeline задает сам — либо абсолютным путем (`source.workspace.path`), либо ключом,
объявленным на worker (`source.workspace.workspaceKey`). Оба варианта умеют `commit` и `push`.
Единственное, чего pipeline не может выдать себе сам, — это **разрешение на push**: папка работает
git-кредами своей машины, а спеку может написать любой, у кого есть админка или MCP-ключ. Поэтому
разрешение живет на worker.

## 1. Разрешите push на worker

Откройте в админке `Agentiz -> Workers`.

В карточке нужного worker в блоке `Откуда разрешён Git push` добавьте абсолютный путь-префикс,
например `/srv/projects`. Разрешение действует на саму папку и на все вложенные, поэтому одного
префикса обычно достаточно на все проекты этой машины. `/` не принимается.

Push выполняется в remote `origin`. Если нужен другой remote, объявите папку в блоке
`Готовые папки для пайплайнов` под ключом и включите там `Разрешить Git push` с именем remote —
это второй, эквивалентный способ выдать то же разрешение:

- `ключ` — стабильное имя, на которое потом ссылается pipeline, например `monorepo`;
- `путь` — абсолютный путь на машине worker, например `/srv/projects/monorepo`;
- `Разрешить Git push` + имя remote, уже настроенного в локальном checkout.

Объявленная папка полезна и без Git: путь можно поправить в одном месте, не трогая спеки.

## 2. Настройте pipeline

Откройте `Agentiz -> Pipelines`, выберите проект и нужный `Pipeline Spec`.

В блоке источника:

1. Выберите `Готовая папка на воркере`.
2. Выберите worker.
3. Укажите папку — либо `Путь прямо здесь`, либо `По ключу, объявленному на воркере`.

Если нужен именно Git review flow, в блоке `После выполнения` выберите `Commit и push из
workspace`. Единственное условие — worker разрешает push из этой папки (префикс в
`Откуда разрешён Git push` или `git.pushEnabled` у объявленной папки). Если условия нет, под списком
написано, где его выдать.

После выбора `Commit и push из workspace` настройте:

- репозиторий — по умолчанию `Remote самой папки`, то есть без привязки. Выбранный
  `AgentRepository` включает сверку remote папки с его `cloneUrl`;
- режим ветки:
  - `В исходную ветку` — push в текущую branch;
  - `В новую короткую ветку` — Agentiz сгенерирует короткое имя ветки по префиксу;
- `Требовать подтверждение` — если включено, run остановится на review и ничего не отправит в
  remote без человека;
- `Префикс ветки` — используется только для режима новой ветки;
- `Commit message template` — шаблон итогового commit message.

Для `worker_workspace` все стадии должны использовать `runtime.mode = host`. Режим `docker` для
такого pipeline недоступен, потому что контейнер не видит подготовленную папку worker.

## 3. Чужие изменения в папке перед запуском

Папка на воркере живёт своей жизнью: в ней может остаться недокоммиченная правка, забытый файл,
что-то в индексе после `git add`. По умолчанию Agentiz **не отказывается работать** из-за этого —
воркер убирает найденное в `git stash` и начинает с чистого дерева. Sha стэша пишется в лог запуска
(`git stash apply <sha>`), так что вернуть эти изменения можно в любой момент.

Так сделано по двум причинам: раньше такой файл останавливал весь пайплайн, а если бы запуск всё же
начался — чужие правки попали бы в diff как работа агента.

Отключается в спеке пайплайна: `source.workspace.stashDirty: false` (в админке — галочка под
выбором папки). Тогда возвращается прежнее поведение: запуск падает с «Managed workspace must be
clean», а папку никто не трогает.

## 4. Что происходит во время выполнения

Когда pipeline заканчивает работу в workspace:

- Agentiz сохраняет diff, список файловых операций и контрольные хэши дерева;
- если `requireApproval = false`, система сама ставит job на `commit` + `push`;
- если `requireApproval = true`, задача и run переходят в `waiting_review`.

В review flow сам `push` выполняет тот же worker, на котором лежит checkout. Agentiz не берет на
себя отдельные Git credentials и не делает force-push.

## 5. Как подтверждать изменения

Откройте страницу конкретного run. Для workspace review там появятся два блока:

- `Проверка workspace-изменений` — статус proposal, путь, base branch/SHA, текущая ревизия и
  управляющие действия;
- `Дифф` — список измененных файлов, статистика и сам patch.

Если proposal находится в `waiting_review`, доступны действия:

- `Подтвердить commit и push` — при необходимости можно поправить target branch и commit message;
- `Продолжить работу` — оставить комментарий для следующей ревизии, после чего Agentiz создаст
  новый continuation run;
- `Отклонить и вернуть workspace` — worker уберёт всё несохранённое в `git stash` и вернёт папку к
  исходному base SHA. Игнорируемые файлы останутся на месте, работа агента не пропадёт: sha стэша
  появится в карточке proposal (`git stash apply <sha>`), а коммит, если агент успел его сделать,
  останется доступен по ссылке `refs/agentiz/abandoned/<id>`.

Если `push` или `reset` не удались, на той же странице будут показаны `push_failed` или
`reset_failed` и кнопки повторного действия.

## 6. Если папка осталась заблокированной

Пока proposal не решён, он держит свою папку: любой другой запуск по этому пути падает ещё при
постановке в очередь с `Workspace "<ключ>" (<путь>) is reserved by proposal <id>`. В самом
сообщении теперь есть статус proposal, название задачи и ссылка на нужный run — открывать её и
есть штатный способ разобраться.

Это нормальное состояние для `waiting_review`: изменения ждут человека, и правильный выход —
подтвердить или отклонить их. Хуже, когда решать уже нечего: run отменили, воркер перезагрузили,
job никто не забрал. Тогда proposal остаётся в `working` или `*_queued`, а `Отклонить` на такие
статусы отвечает 409 — отклонять там нечего.

Отмена run теперь тоже считается ответом: если run отменили и он ещё не был у воркера,
Agentiz сам ставит reset на его proposal. Если run в этот момент выполняется, proposal не трогают —
воркер всё равно отчитается, и только он может убрать свой маркер с диска.

Что происходит дальше без человека:

- proposal в `working`/`continuing`, чей run уже завершился, сервер сам ставит в очередь
  безопасный reset;
- решение, которое никто не забрал за 15 минут (`AGENTIZ_PROPOSAL_ACTION_TIMEOUT_MS`),
  переоткрывается как `push_failed`/`reset_failed` — то есть возвращается в состояние, где кнопки
  снова работают.

Автоматика может себе это позволить именно потому, что reset ничего не уничтожает: перед
возвратом папки воркер делает `git stash`. А вот сам резерв автоматика не снимает никогда — на
диске у воркера лежит маркер, который переживает запись в базе, и «тихое» снятие резерва просто
поменяло бы понятную блокировку на непонятную. Поэтому в карточке proposal есть две кнопки:

- `Освободить workspace` — то же, что отклонение, но доступно из «застрявших» статусов: текущая
  работа останавливается, воркер прячет несохранённое в stash, возвращает папку к base SHA и
  снимает маркер, резерв уходит по его отчёту. Если воркер прямо сейчас держит lease на папку, кнопка откажет и попросит
  дождаться остановки job.
- `Снять резерв принудительно` — резерв снимается сразу, без воркера. Нужна только тогда, когда
  машина не вернётся: stash делать некому, папку никто не восстановит, незакоммиченная работа и
  маркер останутся на ней, и следующий запуск будет падать уже на «workspace не чистый», пока её
  не почистят руками.
  Маркер при этом больше не блокирует папку навсегда — сервер помечает такой запуск
  `staleMarkerAllowed`, и воркер удаляет чужой маркер сам.

Те же действия есть в MCP: `agentiz.manageProposal` с `action: "release"` и, при необходимости,
`force: true`. Найти держателя папки — `agentiz.proposals` с `holding: true`.

Даже после принудительного снятия папка не остаётся заблокированной навсегда: следующий запуск по
этому пути видит забытый маркер, убирает остатки в stash под именем **старого** proposal, отматывает
HEAD к его базе (коммит, если он был, остаётся в `refs/agentiz/abandoned/<id>`) и продолжает
работать. Sha этого stash приезжает на сервер и записывается в ту же карточку. А до того момента имя
stash уже известно — оно указано в `lastError` proposal, и его достаточно, чтобы найти работу через
`git stash list` прямо на машине.

## Ограничения и проверки

- `worker_workspace` не поддерживает `commit_and_pr`.
- Push возможен только из папки, которую worker разрешил: префикс в `gitPushRoots` или
  `git.pushEnabled` у объявленной папки. Спека, сохраненная без такого разрешения, сохранится, но
  run упадет при постановке в очередь с сообщением, какой префикс нужно добавить.
- Ограничение воркера по репозиториям (`allowedRepositoryIds`) работает как везде: пустой список
  значит «любой репозиторий проекта».
- Remote checkout должен оставаться на ожидаемом base commit; если branch уже уехала вперед,
  Agentiz остановит операцию.
- Если сохраненный diff был обрезан по размеру, подтверждение `push` блокируется: сначала нужен
  полный reviewable diff.

## Где смотреть связанные данные

- `Agentiz -> Workers` — разрешение на Git push и объявленные workspace.
- `Agentiz -> Pipelines` — источник `worker_workspace` и финальное действие `commit`.
- Страница конкретного `run` — diff, подтверждение, continuation, reset и освобождение папки.
- `Agentiz -> Workspace Proposals` — сами proposal-записи как бизнес-сущность Adminizer.
