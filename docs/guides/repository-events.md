# События репозитория: «пришли коммиты», «завершился CI», «опубликован пакет»

Про что этот документ: как факт из GitHub («в ветку запушили», «сборка упала», «выехал образ»)
доезжает до воркфлоу, почему у первых двух фактов источников **два** и что держит их от того,
чтобы поднять флоу дважды.
Читателю предполагается знакомство со стеком, но не с этим репозиторием.

Смежные тексты: [круг доработки и решение человека](./workflow-human-gate.md) — граф, который здесь
замыкается через CI; [участники и границы доступа](./project-access.md) — чем ограничены панельные
роуты, которые редактор ноды дёргает.

## Одна картинка

```
GitHub ──вебхук──────────────►  POST /api/agentiz/hooks/v1/:endpointId   (app-agentiz-webhooks)
                                          │  подпись, дедуп, журнал
                                          ▼
                                 маппер github-repository                (app-agentiz-github-integration)
                                          │
GitHub ◄──опрос раз в 15 мин──  GithubRepositoryEventService.pollAll()   (тот же слой)
                                          │
                                          ▼
                       publishRepositoryPush / publishRepositoryCiRun    (ЯДРО)
                             размножение по проектам · атрибуция запуска
                             строка в ленте · сдвиг курсора
                                          │
                                          ▼
                        agentiz.repository.pushed / .ciRun  →  триггер-нода  →  граф
```

Существенное здесь — где нарисована граница ядра. **Что событие значит** — ядро
(`layers/app-agentiz/lib/workflow/repositoryEvents.ts`). **Как о нём узнали** — слой платформы.
Слой GitLab, когда он появится, добавит читателя, а не второй экземпляр смысла.

## Два источника, один курсор

Вебхук — быстрый путь, опрос — страховка, и опрос **не выключается** там, где стоит хук: GitHub не
повторяет доставку сам, а сервер бывает недоступен ровно в минуту деплоя.

Одним источником их делает **курсор** — колонка `AgentRepository.watchCursor`:

```jsonc
{ "branchHeads": { "main": "aaa…", "release/1.2": "bbb…" }, "lastCiRunId": 4217, "checkedAt": "…" }
```

Курсор двигают **только** `publishRepositoryPush` / `publishRepositoryCiRun` — те же две функции,
что эмитят событие. Поэтому доставленный хук сдвигает голову ветки, и ближайший опрос видит
совпадение и молчит. Обратное тоже верно. Если завтра кто-нибудь захочет «просто сдвинуть курсор»
мимо этих функций — это ровно тот способ, которым два источника снова разойдутся.

Курсор живёт на `AgentRepository`, а не на связке с проектом, и по той же причине, по которой хук
один: репозиторий, подключённый к двум проектам, спрашивают у платформы **один раз**.

**Первый проход ничего не эмитит.** `seedWatchCursor` заполняет курсор целиком, одной записью, и
молчит: иначе подключение репозитория подняло бы флоу на всю его историю веток и на каждый
завершённый прогон CI. Отдельная функция, а не «публикация с пустым списком коммитов», именно
потому, что разница — в отсутствии события, ленты и пробуждения графа.

## Третий факт: пакет, и почему у него источник один

`agentiz.repository.packagePublished` — «в реестре появилась новая версия пакета репозитория»; для
контейнера это новый тег образа. Он устроен как два первых ровно до того места, где начинается
курсор, и там кончается сходство:

- **опроса за ним нет.** Опрос читает git-API и о реестрах ничего не знает; чтобы наблюдать реестр,
  нужен отдельный читатель по OCI Distribution API со своим курсором `{тег: дайджест}`, и его
  сейчас не существует. Поэтому пропущенная доставка **теряется**, а не догоняется, а на
  репозитории без хука события о пакетах не будет вовсе.
- **курсора у него тоже нет**, и это следствие первого: курсор существует, чтобы два наблюдателя
  не сообщили факт дважды, а второго наблюдателя здесь нет. Идемпотентность повторной доставки даёт
  уникальный `(endpointId, dedupeKey)` в журнале доставок — тот же механизм, что и у остальных.
- **атрибуции нет и быть не может.** У образа нет ветки, поэтому связать его с `AgentRun` не по
  чему: в payload нет ни `ownRunId`, ни `taskId`, а поля `branches`/`ignoreOwnRuns` на этом событии
  **не проверяются** (не «проходят всегда» — просто не читаются). Предохранитель от
  самозацикливания здесь — `skipIfFlowActive` и `maxRounds` на триггере.

Второе условие доставки — привязка пакета к репозиторию. Контейнер в GHCR принадлежит организации,
и хук репозитория его не видит; привязку даёт публикация из workflow этого репозитория или метка
`org.opencontainers.image.source` в образе. Если этого нет, событие уходит на уровень организации,
где хуков мы не ставим.

Фильтры — `packageName` и `tag`, маски через запятую, как `branches`, но без правила про слэш и без
учёта регистра: у тега образа нет структуры пути. Пакет без тега (не контейнер) под непустую маску
тега не подходит — пустое значение не «совпадает со всем».

## Что событие несёт и почему в нём есть `projectId`

Факт — про репозиторий, но все ноды фильтруют по проекту. Поэтому событие **размножается**: одна
активная `AgentProjectRepository` — одно событие, со своими `projectId` и `projectRepositoryId` при
общем `repositoryId`. Форма payload описана в `lib/workflow/events.ts`
(`AgentizRepositoryPushedPayload`, `AgentizRepositoryCiRunPayload`) и плоская — ноды читают пути
(`{{payload.branch}}`).

## Свои пуши: `ownRunId`, и почему умолчания у двух событий разные

Своим считается пуш в ветку, записанную в `AgentRun.branch` этого проекта — совпадение по **ветке**,
не по sha. Человек, дописавший коммит в ветку агента, работает внутри уже идущего круга; поднимать
поверх него второй незачем. Sha едет в payload как факт, так что граф, которому нужно строгое
прочтение, сравнит сам.

Дальше — асимметрия, которая и есть суть §6 плана:

- **пуш**: `ignoreOwnRuns` по умолчанию **включён**. Иначе граф кормит сам себя — агент запушил,
  триггер сработал, пайплайн запустился, агент запушил.
- **CI**: по умолчанию **выключен**. «Упала сборка нашей же ветки» — это и есть повод для доработки.

Поскольку умолчание зависит от `event`, в `configSchema` у поля **нет** `default`: канвас записал бы
одно значение для обоих событий. Значение вычисляется в `bind()` — тем же приёмом, что
`triggerFilters` для комментария.

## Как круг замыкается через CI, без единой новой ноды

Когда `ownTaskId` заполнен, он же кладётся в payload под именем `taskId` — адрес, который читают все
ноды ниже по графу (`payloadOf`). Поэтому

```
agentiz.repository.trigger (ciRun, conclusion: failure) → agentiz.task.comment
```

пишет провал в тред задачи, чей запуск эту ветку сделал, а комментарий поднимает уже существующий
вход «в задаче написали комментарий». Предохранитель круга — `maxRounds` на том входе.

Если запуска не было (обычный пуш постороннего), `taskId` в payload **отсутствует** — не `null`, а
именно отсутствует, потому что `payloadOf` принял бы `null` за задачу, которую не удалось загрузить.
Продолжение графа тогда обычное: `agentiz.task.create` → `agentiz.pipeline`. Запуска без задачи не
бывает: `AgentRun.taskId` — `NOT NULL`, и на задаче держатся тред, вложения, proposal и входящие.

## Хук: чей он, чем подписан и почему может не встать

- **Один хук на `AgentRepository`**, не на связку: доставка одна, размножение — дальше.
- **Жизненный цикл идёт за связками**, и следит за этим модельный хук на `AgentProjectRepository`
  (`@AfterCreate/@AfterUpdate/@AfterDestroy`), а не панельный роут: связку пишут четыре разных
  вызывающих, и только модельный хук покрывает всех. Работа откладывается на `afterCommit` — внутри
  транзакции это либо держало бы её открытой на время похода в GitHub, либо (на sqlite, где
  соединение одно) выполняло бы запросы **рядом** с открытой транзакцией и ломало её.
- **Сверка сериализована на репозиторий** (`syncRepositoryWebhook`). Два одновременных прохода —
  это не дублирующаяся работа, а порча: каждый удалит «устаревший» хук другого и запишет свой
  секрет поверх чужого, оставив хук, секрета которого никто не хранит.
- **Секрет принадлежит репозиторию.** Мы выдали его GitHub'у, поэтому подпись
  `X-Hub-Signature-256` сверяется с `AgentRepository.webhook.secret` — и поэтому маппер объявляет
  `auth: 'mapper'`, а не отдаёт проверку принимающему слою. Колонка `webhook` наружу не выходит
  никогда: все поверхности идут через `maskRepositoryWebhook`.
- **Набор событий хука хранится рядом с ним** (`webhook.events`). Иначе быстрый путь сверки — «уже
  стоит по этому URL» — неотличим от «уже стоит с нужными событиями», и каждый репозиторий,
  подключённый до появления нового факта, доставлял бы старый набор вечно. Отставший набор
  **патчится** (`PATCH /hooks/:id`), а не переустанавливается: переустановка ротирует секрет, и
  доставка, летящая в этот момент, приходит с подписью, которую нечем проверить. Отсутствующее
  поле = хук поставлен до появления поля, то есть устарел по определению.
- **Сверку запускает и опрос.** Модельный хук срабатывает только когда связку кто-то **пишет**,
  поэтому репозиторий, подключённый давно, иначе никогда не заметил бы ни отвалившегося хука, ни —
  что тише — хука со старым набором событий. Проход опроса сверяет по дороге; в общем случае это
  бесплатно, потому что совпавший URL и набор событий не стоят ни одного запроса к платформе.
- **Установка заканчивается `pings`.** «Хук создан» — это ещё не «хук доставляется»; недоступный
  снаружи сервер должен упасть здесь, при подключении репозитория, а не на первом настоящем пуше.
- **Отсутствие хука — поддерживаемое состояние, а не поломка.** Нет `AGENTIZ_PUBLIC_URL`, не
  смонтирован слой приёма, у подключения урезан скоуп — во всех трёх случаях причина пишется в
  `webhook.lastError`, репозиторий продолжает наблюдаться опросом, и это видно в панели и в
  редакторе ноды. Нового скоупа при этом не нужно: `repo` покрывает и установку хука, и чтение
  журнала доставок.

## Слой приёма: что он умеет и чего намеренно не умеет

`layers/app-agentiz-webhooks` знает про доставку три вещи: публичный URL с **сырым** телом, проверку
отправителя и журнал. Что доставка *значит* — дело маппера из коллекции `webhookMappers`.

- Тело сырое, потому что подпись считается по байтам как они пришли; `JSON.parse` + `JSON.stringify`
  их меняет. Свой `express.raw` на префиксе роутера, разбор — после проверки.
- Роутер смонтирован на `appManager.app`, а не через `adminizerMiddlewares`: тот диспетчер
  префиксует всё `/dashboard`, и внешний интегратор слал бы внутрь админки.
- `endpointId` в пути не секрет: он нужен, чтобы **до** разбора тела знать маппер и чей секрет
  сверять — иначе подпись проверять нечем.
- Журнал (`AgentWebhookDelivery`) пишется **всегда**, включая `rejected` и `ignored`. GitHub шлёт
  десяток типов событий там, где мы следим за двумя, так что большинство строк — `ignored`, и это
  здоровое состояние. «Мы отправили, у вас пусто» разрешается только журналом.
- Идемпотентность — на составном **уникальном** индексе `(endpointId, dedupeKey)`, а не на
  «прочитать и записать»: две копии одной переотправки приезжают одновременно. Индекс объявлен и в
  миграции, и на модели — иначе `sync({alter:true})`-развёртывание дедуплицировало бы молча никак.
- Маппер `github-repository` **задачу не создаёт** — это отклонение от базовой модели того слоя
  (там маппер = задача) и оно сознательное: событие репозитория не является просьбой что-то
  сделать, а что делать дальше — решает граф.

## Куда смотреть, когда «запушили, а флоу не стартовал»

По порядку — каждый шаг отвечает на «дошло ли до сюда»:

1. **Лента.** `AgentActivity` с типом `repository.pushed` / `repository.ci_run` пишется до всякой
   политики уведомлений. Есть строка — факт доехал до ядра, дело в графе. Нет — идём дальше.
2. **Журнал доставок.** `AgentWebhookDelivery` по этому эндпоинту: `rejected` c 401 — разошлись
   секреты (переставьте хук: `syncRepositoryWebhook`); `ignored` — событие не из тех двух;
   пусто — GitHub до нас не достучался, смотрите `…/hooks/{id}/deliveries` на его стороне.
3. **Состояние хука.** `AgentRepository.webhook.lastError` — обычно там прямым текстом написано,
   почему хука нет.
4. **Курсор.** `AgentRepository.watchCursor.branchHeads[ветка]` уже равен новой голове — значит
   событие уже отдавали, и повторно его не будет. Это не поломка, а работа дедупликации.
5. **Фильтры ноды.** Проект, репозиторий, маски веток, исход CI — и `ignoreOwnRuns`, который для
   пуша по умолчанию **включён**: пуш, сделанный нашим же запуском, отфильтрован намеренно.

## Куда добавлять

- **Новая платформа** (GitLab): свой сборщик фактов + свой маппер, вызывающие
  `publishRepositoryPush` / `publishRepositoryCiRun`. В ядре не меняется ничего; `syncWebhook` на
  `GitConnectionAuthority` — необязательный метод, без него всё живёт на опросе.
- **Новый факт о репозитории** (релиз, PR): новая константа события + payload в
  `lib/workflow/events.ts`, класс в `agentizWorkflowEvents` (без объявления событие не попадёт в
  дропдаун канваса), своя `publish*` рядом и, если нужен свой отсчёт, своя половина курсора.
- **Новый отправитель вебхуков вообще**: маппер в коллекцию `webhookMappers` и, если его секрет
  принадлежит эндпоинту, `auth: 'endpoint'` — тогда проверку делает принимающий слой, и писать в
  маппере нечего.
