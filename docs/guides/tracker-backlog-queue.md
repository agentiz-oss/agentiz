# Бэклог в трекере, очередь в Agentiz: «по одной задаче, следующая — когда закрыли предыдущую»

Как устроен проект, который люди ведут в GitHub (issues, доска Project), а двигает вперёд workflow
Agentiz. Писать бэклог и решать, что сделано, остаётся людям и трекеру. Agentiz решает только
**когда** брать следующую задачу.

## Разделение ответственности

| Что | Где живёт | Кто меняет |
| --- | --- | --- |
| что делать (бэклог, порядок, обсуждение) | issues репозитория | люди |
| сделано ли | состояние issue: `closed` | человек мержит PR с `Closes #N` или закрывает руками |
| когда брать следующую | граф `trigger.cron → agentiz.task.next → agentiz.pipeline` | Agentiz |
| доска | GitHub Project, встроенные правила GitHub («auto-add», «closed → Done») | GitHub |

Из этого следует главное правило: **«закрыта» — слово трекера, а не наше.** Если у задачи есть
`AgentTask.externalStatus`, решает только он. После пуша ветки задача становится `status: done`
локально, но issue в этот момент открыт, PR ждёт ревью, и следующую задачу брать **нельзя**. Если
трекера нет (локальная задача), закрытой считается задача в `done`/`cancelled`/`ignored`
(`taskClosed` в `lib/workflow/nodes.ts`).

## Как узел решает (`agentiz.task.next`, `layers/app-agentiz/lib/workflow/nodes.ts`)

На каждом срабатывании расписания:

1. **Синхронизирует проект сам**, через `GitSyncService.syncProject` (это те же contributors,
   что у кнопки синхронизации; для GitHub это `GithubIssueSyncService`). Поэтому очередь не зависит
   от `AGENTIZ_GITHUB_SYNC_ENABLED` на сервере и узнаёт о закрытии issue на ближайшем тике, а не
   через 15 минут опроса. Если синхронизация вернула ошибку, узел отвечает `busy`, а не решает по
   устаревшим данным.
2. **Помечает «свои» задачи по тексту** `AgentTask.workflowStatus`: взятая получает «в работе»,
   закрытая в трекере — «закрыта». Отдельной колонки для этого нет, текстовый статус воркфлоу и так
   виден в карточке, и запись в него ничего не будит (он вне `WORKFLOW_WATCHED_FIELDS`). Изнанка:
   если поменять текст в настройке узла на живом проекте, задача, взятая со старым текстом,
   перестанет держать очередь.
3. **`busy`**, если есть «в работе» с открытым issue (неважно, чем кончился запуск: упавшая задача
   ждёт человека и не перепрыгивается) или любая задача проекта в `queued`/`running`/`waiting_review`.
   Второе условие нужно потому, что все запуски такого проекта работают в одной папке воркера.
4. Иначе **берёт самую старую** по дате создания в трекере (`raw.created_at`, не порядок строк:
   первая синхронизация пишет их пачкой) среди задач в `new` без текстового статуса. Берёт
   условным `UPDATE … WHERE workflowStatus IS NULL`, чтобы два тика не взяли одну задачу.

## Как задача закрывается сама: PR с `Closes #N`

Пайплайн с `source.kind: worker_workspace` умеет только пушить ветку, открыть PR из папки воркера
он не может. Поэтому есть `finalAction.openPullRequest` (только с `commit` + `targetBranch.mode:
"new"` + `source.repositoryId`, проверяется в `PipelineSpecValidation.ts`). PR открывает **сервер**
в момент, когда воркер доложил, что пуш прошёл: `AgentPipelineService.openWorkspacePullRequest`,
вызов в `AgentWorkerApiService.applyWorkspaceActionResult`. Раньше нельзя: доставка из папки — это
отдельная задача, которая начинается уже после завершения запуска, а PR на ветку, которой ещё нет в
remote, платформа не примет. `Closes #N` ставится, только если issue принадлежит **тому же**
репозиторию (маркер `agentizIntegration` в `AgentTask.raw`). Номер из чужого трекера закрыл бы
чужой issue.

Отказ платформы (PR уже открыт, нет прав) не роняет доставку: пуш уже записан, причина уходит в
лог запуска строкой `warn`.

## Обратное направление: задачи пишет агент, закрывают люди

Тот же проект держит и второй поток: агент по скилам готовит публикации («что и где опубликовать»),
люди публикуют их сами или отклоняют. Задача на публикацию — это тоже issue, с меткой
`publication`. Закрыт как completed — опубликовано, ссылка в комментарии. Закрыт как not planned —
отклонено, причина в комментарии. Двигает поток узел `agentiz.tasks.open`: он держит **запас** до
`max` открытых задач и, когда люди закрыли часть, пропускает флоу к `agentiz.task.create`. Тот
заводит локальную задачу-подготовку (`publication-prep`) для пайплайна, в котором агент сначала
записывает исход закрытых issues в свои карточки, а потом сам заводит новые через `gh issue create`.

Почему задачу заводит агент, а не узел: текст, площадка и ссылка — результат работы агента, и
создать issue по ним он может сам из той же папки через уже залогиненный `gh` (то же правило, что
для `gh repo create` в `AGENTS.md`). Серверу не нужно учиться создавать issues в трекерах.

Три причины ждать (`busy`), и у каждой своя цель:
- `run_active`: в проекте идёт любой запуск, а папка одна на всех;
- `preparing`: задача-подготовка не закрыта. Упавшая тоже не закрыта, поэтому поломка не
  превращается в новую подготовку на каждом тике;
- `too_soon`: от прошлой подготовки прошло меньше `minIntervalHours`. «Раз в сутки» сделано как
  ежечасный триггер плюс интервал, а не как `dailyAt`: при `dailyAt` занятый в этот час воркер
  стоил бы целых суток.

Метки обоих видов задач стоят в `skipTags` у `agentiz.task.next`, иначе очередь разработки взяла бы
их себе.

## Что проверить, если очередь стоит

- `agentiz.workflowDetails`: что последние прогоны ответили (`busy` с `reason`/`busyTaskId`).
- `reason: in_progress`: issue задачи `busyTaskId` открыт. Если работа принята, смержите PR или
  закройте issue. Если запуск упал, перезапустите задачу из панели или с телефона.
- `reason: run_active`: какая-то задача проекта висит в `waiting_review`. Чаще всего это запуск
  без изменений, у которого предложение держит папку; см. «Входящие» и раздел про proposal в
  `AGENTS.md`.
- `reason: sync_failed`: у подключения GitHub протух токен или нет доступа к репозиторию
  (`agentiz.repositories`, поле `lastError` у привязки).
- PR не появился: строка `Pull request не открыт: …` в логе запуска.
